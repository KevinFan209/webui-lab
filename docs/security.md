# 資安檢查清單 (Security Checklist)

逐項評估專案是否存在以下風險，並記錄因應方式。

- [ ] **XSS**：使用者輸入是否有適當跳脫/驗證，避免注入惡意 script？
- [ ] **CSRF**：跨站請求是否有防護機制（如 token）？
- [ ] **CORS**：API 的跨來源設定是否合理，未過度開放？
- [ ] **Auth（身分驗證）**：登入/權限機制設計，session/cookie/JWT 的取捨與理由？
- [ ] **輸入驗證**：前端與（若有）後端是否都對輸入做驗證，而非只信任前端？
- [ ] **HTTPS**：正式環境是否使用 HTTPS？
- [ ] **密鑰管理**：API 金鑰/密碼是否曾出現在前端程式碼或 git 歷史中？
- [ ] **依賴套件風險**：使用的第三方套件/CDN 是否可信？

## 這個專案的具體檢查項目

- [x] **不暴露私人管理後台**：Mac mini 上既有的 `panel/`（port 8209，含 RCON console、世界管理、備份還原等高危操作）跟這個公開網站完全不互通，公開網站也不放任何連結過去。
- [x] **不做自動化的高危操作**：白名單申請只「收件、存成待審清單」，不會自動對 Minecraft 伺服器執行任何指令；核准動作仍由管理員手動執行，避免任意使用者透過表單直接觸發伺服器端指令。
- [x] **輸入驗證**：`minecraft_id` 在後端用 regex（`^[A-Za-z0-9_]{3,16}$`，符合 Minecraft 正式使用者名稱格式）驗證，格式不對直接回 400，不寫入檔案——也預先避免未來若串接 RCON 時的指令注入風險。
- [x] **使用者資料不進 git**：`data/whitelist_requests.json` 已加進 `.gitignore`，避免把申請者的資料 commit 進版本控制。
- [ ] **CORS**：目前前端只呼叫自己同網域的 API（same-origin），不需要額外的 CORS 設定；之後若公開網站跟 Mac mini 直接互通，需要重新評估。
- [ ] **Auth（身分驗證）**：目前沒有帳號系統，MVP 階段審核完全靠管理員自己看 JSON 檔案；對應課程後段 JWT/Session 主題再補上正式的管理員登入。
